# 11 · 关卡编辑器与内容管线

> 《Bug哥：别相信你的第一眼》内容生产体系：如何让策划高效生产关卡、让机器拦截坏数据、让 AI 在第三阶段批量扩充内容。
> 本文引用基准：00（术语）、04（关卡 Schema，本文件为 04 的落地细则，两者必须一致）、07（gd_level.status）、01（内容管线）。如有冲突以 README + 00 为准。

## 1. 内容管线总览

```
设计 → 编辑 → 校验 → 审核 → 发布 → 下发
 │      │      │      │      │      │
 │      │      │      │      │      └─ 客户端版本化下载 / 服务端配置下发
 │      │      │      │      └─ gd_level.status: 3 发布，生成版本记录(content_md5)
 │      │      │      └─ 人工审核（玩法体验 + 现实逻辑 + 合规词表）
 │      │      └─ Schema 校验器（机器强制拦截，错误即拒绝入库）
 │      └─ 关卡编辑器（Web, 1025）
 └─ 关卡设计规范（模板 + 示例库 + 难度曲线表）
```

- 一关数据 = 一份关卡 JSON（Schema v1），客户端解释器执行，不硬编码任何关卡；
- 内容生产质量由「校验器强制拦截 + 人工审核兜底」双闸保证，支撑 1000+ 关卡规模。

## 2. 关卡编辑器功能需求

### 2.1 关卡可视化编辑

- 画布区：按 puzzleType 渲染关卡场景模板（场景图、可点击对象、状态元素），拖拽摆放交互对象；
- 属性面板：编辑关卡基础属性（title / level_no / chapter_id / difficulty / puzzle_type / schema_version / is_hidden），puzzle_type 一律使用标准枚举 visual/reverse/target/language/detail（与 04 文档 R05 一致，模板 key 仅用于编辑器内部组织）；
- 结构树：展示误导层 → 交互对象 → 判定逻辑 → 真相层，支持增删改与排序；
- JSON 面板：可视化操作与原始 JSON 双向同步，可直接手改 JSON 并实时回显。

### 2.2 谜题类型模板

- 内置模板（模板 key 与 puzzle_type 标准枚举的映射）：`visual_trick → visual`（视觉误导）、`common_sense → reverse`（常识反转）、`goal_misread → target`（目标误解）、`language_trap → language`（语言陷阱）、`detail_reason → detail`（细节推理）；
- 模板即 Schema 子结构，选定 puzzle_type 后自动生成对应字段骨架（puzzle_type 一律存标准枚举值 visual/reverse/target/language/detail，模板 key 仅用于编辑器内部组织），降低策划填写错误率；
- 新谜题类型 = 注册新模板 + 解释器新增渲染分支（需客户端发版，故模板列表变更走版本评审）。

### 2.3 提示配置

- 每关配置 1/2/3 级提示（提示逐级递进：观察方向 → 缩小范围 → 接近答案），禁止任意一级直接泄底；
- 提示内容绑定 `hint_ids`，与 gd_level.hint_ids 字段一致；未配置完整三级提示时校验器给出 Warning 而非 Error（允许新手关只有 2 级）。

### 2.4 Bug哥台词配置

- 台词库：默认错误反馈、连续错误吐槽、通关 Aha 台词、卡关安慰台词四类，支持按关卡覆盖；
- 台词配置为字符串数组，编辑器提供语气示例库（嘴硬/自信/搞笑/自嘲），保证 Bug哥 IP 人设一致；
- 台词长度由校验器拦截（规则 B09），词表合规由敏感词规则拦截（规则 B12）。

### 2.5 预览试玩

- 编辑器内嵌 iframe，加载 Cocos H5 构建产物，直接试玩当前关卡 JSON（同构建、同解释器，杜绝双实现）；
- 试玩模式支持：正常通关、错误路径触发、提示逐级触发、Bug哥台词回显；
- 预览只读，不写后端存档，试玩行为不产生埋点污染。

## 3. 编辑器技术架构

```
┌──────────────────────────── Vue 3 单页（端口 1025）────────────────────────────┐
│ 关卡列表 │ 可视化编辑画布 │ 属性面板 │ JSON 源码面板 │ 校验结果面板 │ 发布按钮  │
└───────────────────────────────────┬───────────────────────────────────────────┘
                                    │ 关卡 JSON（Schema v1）
                                    ▼
                    校验器（utils/validator，本地实时 + 提交时强制）
                                    │
                                    ▼
                   iframe 实时预览 ← 加载 Cocos H5 构建产物（同解释器）
                                    │
                                    ▼
                后端 API（2010）：草稿保存 / 提交审核 / 发布 / 下线
```

- 前端：Vue 3 + Vite + TS，`project/editor/`（端口 1025）；
- 后端：NestJS 关卡模块提供 `gd_level` CRUD 与状态流转接口（见 08 API 文档）；
- 校验器：前后端共用同一份实现（npm 包形式放 `utils/`），本地实时反馈 + 服务端强制校验双保险；
- 预览：iframe 指向 Cocos H5 构建产物（`project/frontend` 的 web-mobile 构建），以 URL 参数注入关卡 JSON。

## 4. Schema 校验器设计

### 4.1 定位

- 校验器是内容管线的**唯一机器闸门**：AI 生成、人工手写、UGC 提交，全部先过校验器；
- 输入：关卡 JSON（Schema v1）；输出：`通过 / 错误清单 / 警告清单`；
- **规则体系**：04 文档定义 JSON Schema 结构级规则（R01~R20，字段/枚举/引用/内容校验）；本清单定义**管线业务级规则**（DB 字段、合规词表、资源引用、发布约束）。两层规则合并构成完整校验器，编号各自独立，实施时先跑 04 层（结构）再跑本层（业务）。
- 校验器统一目录：`utils/validator`（04 文档 §9 的 `utils/level-validator` 为本目录的别名，统一使用 `utils/validator`）。

### 4.2 规则清单（共 15 条硬规则 + 4 条警告，管线业务级）

| # | 规则 | 级别 | 说明 |
| --- | --- | --- | --- |
| B01 | `schema_version` 必须存在且为受支持版本 | Error | 当前仅支持 v1；解释器向前兼容，禁未来版本入库（对应 04 R01） |
| B02 | `level_no` 必须为正整数且全局唯一 | Error | 与 gd_level.level_no UNIQUE 一致 |
| B03 | `title` 非空，长度 ≤ 128 | Error | 与 gd_level.title VARCHAR(128) 一致 |
| B04 | `puzzle_type` 必须在已注册枚举内 | Error | 枚举：visual / reverse / target / language / detail（与 04 文档 R05 一致） |
| B05 | `difficulty` 必须为 1~5 整数 | Error | 难度星级基准（00 术语表，对应 04 R04） |
| B06 | 误导层必须存在且非空 | Error | 术语基准：每关必须有误导层（对应 04 R13） |
| B07 | 真相层必须存在，且不得含魔法/科幻/随机规则 | Error | 答案必须符合现实逻辑，可常识解释（项目铁律） |
| B08 | 提示 1/2/3 级逐级递进，低级不得直接泄露答案 | Error（缺级为 Warning） | 新手关允许 2 级提示（Warning，对应 04 R15） |
| B09 | Bug哥台词数组非空、长度 ≤ 20 条/关、单条 ≤ 200 字符 | Error | 人设一致性 + 存储约束（对应 04 R17） |
| B10 | 关卡 JSON 序列化后 ≤ 64KB | Error | 防止超大内容拖垮解释器与下发通道 |
| B11 | 禁止脚本注入与危险载荷 | Error | content 内任何字符串不得含 `<script>`、`on*=`、`javascript:` 等可执行载荷 |
| B12 | 文本内容不得命中敏感词表 | Error | 审核词表（utils/validator 内置词库，可配置） |
| B13 | 引用资源（图片/音效/立绘）必须存在于资源清单 | Error | 禁止外链 URL，资源走版本化 CDN 路径 |
| B14 | 数值字段（时间限制、点击次数上限等）必须为非负整数且在允许范围内 | Error | 范围由各 puzzleType 模板定义 |
| B15 | `reward_stars` 必须为 1~3 整数 | Error | 与 gd_level.reward_stars 一致 |
| W01 | 未配置完整三级提示 | Warning | 新手关允许（对应 04 R15 Warning 分支） |
| W02 | 关卡文本未配置任何覆盖台词（走默认台词库） | Warning | 允许但建议覆盖 |
| W03 | 预估通关时长 < 5 秒或 > 3 分钟 | Warning | 卡关风险提示 |
| W04 | 与已发布关卡 title 或真相层相似度 > 90% | Warning | 防内容重复（AI 批量生成期重点） |

### 4.3 错误提示格式

```json
{
  "code": "B07",
  "level": "error",
  "path": "content.truth.description",
  "message": "真相层描述包含魔法设定，违反现实逻辑约束",
  "suggestion": "改为符合现实常识的解释，例如：利用光学折射原理而非'施法'"
}
```

- 校验器输出：错误清单（error）任何一条存在即拒绝提交入库；警告清单（warning）仅提示不阻断；
- 编辑器内实时展示错误位置（JSON path 高亮 + 面板列表），提交审核前必须清零 error。

## 5. AI 生成关卡管线（第三阶段）

### 5.1 文字流程图

```
[素材库：示例关卡 + 谜题类型模板 + 现实逻辑知识库]
        │
        ▼
[LLM 生成器（utils/generator）]  ← 输入：puzzleType + 难度 + 场景主题 + 参考关卡
        │
        ▼
[机器校验器（utils/validator）]  ── 不通过 ──► [自动打回 + 修正提示] ──► 重新生成（限 3 轮）
        │ 通过
        ▼
[LLM 语义预审（现实逻辑 + 违规词二次过滤）]
        │
        ▼
[人工审核（策划试玩 + 现实逻辑判断 + 台词润色）]  ── 不通过 ──► 废弃/人工改写
        │ 通过
        ▼
[入库草稿（status=1）→ 提交审核（status=2）→ 发布（status=3）]
        │
        ▼
[灰度下发（按章节比例）→ 数据验证（卡关率/差评率/通过时长）→ 异常则下线（status=4）]
```

### 5.2 关键约束

- AI 生成的关卡**必须先过机器校验器**，任何规则不通过即拒绝入库，防止垃圾数据进生产；
- 现实逻辑是 AI 生成的硬伤高发区：LLM 语义预审 + 人工试玩双兜底，人工审核不可省略；
- 生成内容与已发布关卡做相似度检测（W04），控制同质化；
- 阶段三目标：AI 辅助产出占比 ≥ 60% 的增量关卡，人工审核通过率 ≥ 40% 视为管线健康。

## 6. 版本发布流程（对应 gd_level.status 1/2/3/4）

| status | 状态 | 触发动作 | 可执行操作 |
| --- | --- | --- | --- |
| 1 | 草稿 | 编辑器新建/保存 | 继续编辑、提交审核 |
| 2 | 审核中 | 编辑者提交 | 编辑者不可改；审核人可打回（回 status 1）或通过（→ 3） |
| 3 | 已发布 | 审核通过 | 客户端可拉取；生成 gd_level_version 记录（content_md5） |
| 4 | 已下线 | 运营/系统下线 | 客户端停止下发；可修改后重新提交审核 |

- 发布/下线走服务端 API（2010），编辑器不直接写库；状态流转带操作审计日志；
- 每次发布生成 `gd_level_version` 版本记录（version 自增、content_md5），支持按版本回滚与灰度；
- 关卡内容变更必须走「编辑 → 重新校验 → 重新审核 → 重新发布」，禁止直接改已发布行。

## 7. 工具目录规划（utils/）

```
utils/
├── validator/                  # 关卡 JSON 校验器（本文件第 4 节规则的实现）
│   ├── rules/                  # 单条规则实现（B01~B15、W01~W04 + 04 层 R01~R20）
│   ├── dict/                   # 敏感词表、puzzleType 枚举、难度表
│   ├── index.ts                # 校验器统一入口（前端/后端/CI 共用）
│   └── tests/                  # 规则单元测试（含合法/非法用例矩阵）
├── generator/                  # AI 关卡生成器（第三阶段）
│   ├── prompts/                # LLM 提示词模板（按 puzzleType/难度）
│   ├── llm-client.ts           # LLM 接口封装（可替换供应商）
│   ├── post-check.ts           # 生成后语义预审
│   └── tests/
├── migrator/                   # Schema 迁移脚本（v1 → v2 等）
│   ├── migrate-v1-to-v2.ts     # 字段迁移 + 旧版本数据重校验
│   └── tests/
└── scripts/                    # 批量导入/导出、定时发布、数据校验巡检
```

- `validator` 以独立 npm 包提供，游戏客户端构建、编辑器、后端、CI 四端复用同一实现；
- `migrator` 负责历史关卡随 Schema 升级的数据迁移，迁移后必须全量重跑校验器。

## 8. 与 04 文档的一致性约定

- 本文件第 4.2 节规则清单即 04 文档 Schema 定义的校验落地；04 创建时应引用本清单作为「校验器」章节细则；
- 双方共享字段口径：schema_version / level_no / title / puzzle_type / difficulty / hint_ids / reward_stars / is_hidden / status（1/2/3/4），均与 07 数据模型字段级一致；
- 任一文档修订字段或枚举，须同步修订 04 / 07 / 11 三份文档与 init-schema.sql。
