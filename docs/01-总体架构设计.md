# 01 · 总体架构设计

> 《Bug哥：别相信你的第一眼》总体架构。回答两个核心问题：**如何支撑 1000+ 关卡的持续生产**、**如何一次开发多端（抖音/微信/H5）**。

## 1. 架构总览（4 层 + 内容管线）

```
┌─────────────────────────────────────────────────────────────┐
│                      客户端（Cocos Creator 3.x）             │
│  ┌──────────┐ ┌──────────┐ ┌──────────┐ ┌──────────────┐   │
│  │ UI 层     │ │ 玩法层    │ │ 关卡解释器 │ │ 平台适配层    │   │
│  │ (场景/组件)│ │ (状态机)  │ │ (JSON→可玩)│ │ (抖音/微信/H5)│   │
│  └──────────┘ └──────────┘ └──────────┘ └──────────────┘   │
└───────────────┬─────────────────────────────────────────────┘
                │ HTTPS
┌───────────────▼─────────────────────────────────────────────┐
│                   API 网关（NestJS）                          │
│  鉴权 │ 限流 │ 日志 │ 版本 │ 统一响应/错误码                    │
└───────────────┬─────────────────────────────────────────────┘
┌───────────────▼─────────────────────────────────────────────┐
│                  业务服务层（NestJS 模块）                    │
│  用户 │ 存档 │ 关卡 │ 排行 │ 每日 │ 广告 │ 埋点 │ 会员/皮肤    │
└───────────────┬─────────────────────────────────────────────┘
┌───────────────▼─────────────────────────────────────────────┐
│                  数据层                                       │
│  MySQL 8.0（业务主存储）   Redis 7（排行/会话/热点）           │
└─────────────────────────────────────────────────────────────┘

┌─────────────────────────────────────────────────────────────┐
│               内容管线（支撑 1000+ 关卡）                      │
│  关卡编辑器(Web,1025) → Schema 校验 → 版本化发布              │
│  → 客户端版本化下载 / 服务端配置下发                           │
└─────────────────────────────────────────────────────────────┘
```

## 2. 分层职责

| 层 | 职责 | 关键约束 |
| --- | --- | --- |
| 客户端 | 渲染、交互、本地逻辑 | 关卡解释器执行 JSON，不硬编码关卡 |
| API 网关 | 统一入口、鉴权、限流 | 与业务逻辑解耦 |
| 业务服务 | 业务规则、广告验证、排行 | 模块化，可独立扩展 |
| 数据层 | 持久化与缓存 | 表结构见 07 |
| 内容管线 | 关卡生产与发布 | 数据驱动核心，见 04/11 |

## 3. 架构核心原则

### 3.1 内容与代码彻底分离（支撑 1000+ 关卡）

- 关卡 = 纯 JSON 数据（Schema v1 定义，见 04）
- 客户端内置**关卡解释器**：读取 JSON → 构建场景 → 绑定交互 → 判定胜负
- 新关卡 = 新数据，不需要发版客户端
- AI 生成/玩家 UGC = 生产更多 JSON，经校验后入库

### 3.2 平台适配层（一次开发多端）

- 抖音、微信、快手、H5 的能力差异（登录、广告、分享、支付）抽象为接口
- 平台适配层提供实现，业务代码只依赖接口
- 详见 05 客户端架构

### 3.3 服务端模块化（可独立扩展）

- NestJS 模块：用户、存档、关卡、排行、每日挑战、广告、埋点、会员
- 广告验证、排行榜、每日挑战等模块可独立发布、独立扩展

### 3.4 版本化内容管线

- 关卡 Schema 带版本号，解释器向前兼容
- 校验器拒绝非法关卡（AI 生成垃圾数据不进生产）
- 客户端缓存关卡包 + 服务端增量下发

## 4. 关键数据流

### 4.1 单局流程

```
进入关卡 → 拉取关卡配置(本地包/服务端) → 解释器构建场景
→ 玩家交互 → 错误反馈（Bug哥吐槽） → 正确解 → Aha 动画
→ 结算（星级/时间/收藏） → 存档上报 → 激励视频(双倍)可选
```

### 4.2 登录流程（抖音）

```
客户端启动 → 平台适配层调 tt.login → 拿 code
→ 后端换 openid → 注册/登录 → 下发 token
→ 拉取存档与进度
```

### 4.3 广告验证流程

```
玩家触发激励视频 → 平台广告 SDK 播放 → 完成回调
→ 客户端上报 → 后端调抖音服务端验证接口校验
→ 校验通过才发放奖励（防伪造）
```

## 5. 扩展性设计（面向 1000+ 关卡）

| 扩展点 | 设计 | 阶段 |
| --- | --- | --- |
| 关卡数量 | 数据驱动 JSON + 解释器 | 一期 |
| 关卡类型 | Schema 支持扩展 puzzleType 枚举 | 一期 |
| AI 生成关卡 | 内容管线接入生成器 + 校验器 | 三期 |
| 玩家 UGC | 编辑器开放 + 审核流 | 三期 |
| 多平台 | 平台适配层 | 一期 |
| IP 生态 | Bug哥 资产独立管理（立绘/台词/皮肤） | 持续 |
| 每日挑战 | 服务端每日定时选关 | 二期 |
| 排行榜 | Redis ZSet + 定期落库 | 二期 |

## 6. 非功能设计

| 项 | 要求 |
| --- | --- |
| 性能 | 关卡解释器首帧 < 1s；单关内存 < 50MB |
| 可用性 | 后端 99.9%（开发期尽力而为） |
| 安全 | 广告验证服务端化；防作弊（时间校验/频率限制） |
| 数据 | 埋点全量上报，离线缓存重试 |
| 可观测 | 后端请求日志、错误追踪（Sentinel/日志平台） |

## 7. 环境与部署

| 环境 | 用途 |
| --- | --- |
| dev | 本地开发（本机 MySQL/Redis，端口见 README） |
| test | 联调测试（后续） |
| prod | 抖音审核/上线（环境变量注入，严禁硬编码） |

## 8. 与商业闭环的关系

```
抖音短视频传播 → 进入小游戏 → Bug哥解谜体验 → 玩家留存
→ 观看激励广告 → 持续挑战 → 形成 IP 资产
```
